🧠 マルチAI・ハイブリッド開発ワークフロー

Codex × Claude Code × Antigravity 使い分け編

複数の AI エージェント（Codex・Claude Code・Antigravity）の強みを活かし、1 つのプロジェクトでハイブリッドに使いこなすプロの開発フローを体感します。バグ修正・並列リファクタリング・Git ワークフローによる PR 作成までを一気通貫で手を動かして学びます。

所要時間の目安: 約 90〜120 分 ／ レベル: 上級（Git・CLI の基本操作を前提とします）

🙋 みなさんの進捗状況を知りたいので、うまく進んでいる場合も、進んでいない場合も絵文字リアクションを積極的に返してください！進んでないよ、というときも遠慮なく！

はじめに

このハンズオンで体験すること

AI コーディングエージェントは「どれか 1 つを選ぶ」時代から、「適材適所で使い分ける」時代に入りました。このハンズオンでは、特性の異なる 3 つのエージェントを 1 つのプロジェクトに同居させ、それぞれの得意分野を活かして開発を進める「ハイブリッドワークフロー」を実践します。

🎯 ゴール（完成イメージ）

「バグを含む小さなアプリ（例: ToDo リスト）を題材に、Claude Code でバグを高速デバッグし、Antigravity で並列リファクタリングを行い、Git ワークフローで安全に統合して GitHub に PR を出す」——この一連を、複数 AI を干渉させずに回せるようになります。

🧩 そもそも、この3つのエージェントは何が違う？

いずれも「自然言語でコードを書かせる AI エージェント」ですが、得意な土俵が異なります。詳しくは次の比較セクションで見ますが、まずはざっくりのイメージを掴んでください。

  • Codex（OpenAI）: クラウド/CLI で動く実装エージェント。タスクを投げて並列に走らせる「委任型」が得意。
  • Claude Code（Anthropic）: ターミナル常駐の対話型エージェント。大規模なコードベースの把握と、対話しながらの高速デバッグが得意。
  • Antigravity（Google）: エディタ統合型のエージェント開発環境。複数エージェントを並列に走らせ、ブラウザ操作まで含めた検証ができる。
💡 なぜ「使い分け」なのか？ 1 つのエージェントで全工程をやらせると、得意でない作業で時間を浪費したり、品質がブレたりします。「調査・デバッグはこれ」「並列実装はこれ」「統合とレビューは人間 ＋ Git」と役割を分けることが、プロの現場で品質とスピードを両立させるコツです。

✅ 必要な環境

Antigravity と個人向け Claude アカウントの利用は18歳以上が対象です。

  • Git（2.23.0 以降を推奨。git switch / git worktree を使います）と GitHub アカウント
  • GitHub CLI をインストールし、gh --version で確認します。gh auth login でログインし、gh auth status で認証状態を確認してください。
  • Claude Code（Claude Code を利用できる有料プランまたは API の課金設定を用意し、ログイン済みであること）
  • Antigravity IDE（この教材では IDE 版を使用します）
  • Codex（任意。CLI または Web 版。比較・補助として登場します）
  • Node.js（題材アプリの実行に使用。お使いのバージョンで OK）
⚠️ 上級者向けの前提: このハンズオンは git add / commit / push / branch といった Git の基本操作を一通り触ったことがある方を想定しています。とはいえ復習できるよう、Step 4 で著者本人の Git 教材（『開発系エンジニアのための Git/GitHub 絵とき入門』）のエッセンスを交えながら丁寧に解説します。

全体像 — ハイブリッド開発フロー

このハンズオンは、次の 5 ステップで進みます。1 つのリポジトリの中で、各エージェントが別々のブランチ／worktreeで並行作業し、最後に Git で安全に統合して PR を出す、という上級ワークフローです。

Step 1（15分）

🌿 環境準備とブランチ戦略

題材リポジトリを用意し、AI ごとにブランチ／worktree を分ける戦略を立てます。

Step 2（25分）

🐛 Claude Code で高速デバッグ

仕込まれたバグを Claude Code で原因特定し、修正してコミットします。

Step 3（25分）

⚡ Antigravity で並列リファクタリング

別ブランチ（worktree）で並列エージェントによるリファクタを行います。

Step 4（25分）

🔀 Git で統合し PR を作成

add/commit/push → merge → PR → コンフリクト解決まで通します。

Step 5（15分）

🛡 複数AI併用のベストプラクティス

環境干渉を防ぐ設定・運用ルールを整理します。

🔗 役割分担（誰がどのブランチで何をするか）
  1. Claude Code → fix/bug-todo ブランチでバグ修正（Step 2）
  2. Antigravity → refactor/todo ブランチ（worktree）でリファクタ（Step 3）
  3. 人間 ＋ Git → 2 つのブランチを main に統合し、PR を作成（Step 4）
💡 キモは「同じファイルを別 AI が同時に触らない」こと。AI ごとにブランチ（できれば worktree）を分けることで、お互いの編集が衝突せず、Git の履歴上でも「誰が何をやったか」が綺麗に残ります。これが本コースの背骨です。

Step 1: 環境準備とブランチ戦略

まず題材となるリポジトリを用意し、「どの AI がどのブランチで作業するか」を先に決めます。ここを設計してから AI を動かすのが、マルチAI開発で破綻しないための第一歩です。

1-1. Git のユーザー設定を確認する

コミットログに自分の情報が記録されるよう、Git のユーザー名とメールアドレスを設定しておきます（設定済みなら飛ばして OK）。

# すべてのリポジトリ共通の設定（--global）
$ git config --global user.name "あなたの名前"
$ git config --global user.email "you@example.com"

# 設定確認
$ git config --global --list
git config は、コミットに記録される著者情報を決めるコマンドです。
＜参考: 著書『開発系エンジニアのための Git/GitHub 絵とき入門』4 章＞

Step 1-2 に進む前に、GitHub CLI をインストールし、gh --version で確認します。gh auth login でログインし、gh auth status で認証状態を確認してください。

1-2. 題材リポジトリを用意する

バグを 1 つ仕込んだ小さな ToDo アプリを題材にします。お手元に題材がなければ、次のように最小構成を作って初期化してください。

# 作業フォルダを作って Git 初期化
$ mkdir todo-multi-ai && cd todo-multi-ai
$ git init
$ git branch -M main

# 題材ファイル（バグ入り）を作成 ※後述
# ... ファイルを作成したら ...
$ git add .
$ git commit -m "chore: 初期コミット（バグ入り ToDo アプリ）"

# GitHub にリポジトリを作って push（gh CLI を使う例）
$ gh repo create todo-multi-ai --private --source=. --push
💡 題材アプリの中身（例）: app.js に「完了済みタスクを除外する関数」を入れておき、そこに 等価演算子の取り違え（== と ===、あるいはフィルタ条件の反転）のようなバグを 1 つ仕込みます。Step 2 でこれを Claude Code に直させます。

1-3. ブランチ戦略を決める（AI ごとに分ける）

このハンズオンの肝です。AI ごとに作業ブランチを分け、Antigravity 側は git worktree で物理的に別フォルダにして並行作業できるようにします。

ブランチ作成 / 切り替え（git branch・git switch）

# Claude Code 用ブランチを作成して切り替え（-c で作成と同時に切替）
$ git switch -c fix/bug-todo

# 現在のブランチ一覧を確認（* が現在のブランチ）
$ git branch
git branch <名前> でブランチ作成、git switch <名前> で切り替え。git switch -c <名前> なら作成と切替を一度に行えます（Git 2.23.0 以降）。ブランチ名は fix/...・refactor/... のように目的が分かる命名にしましょう。
＜参考: 同書 4 章「ブランチを作成する／切り替える」＞

worktree で「別フォルダの別ブランチ」を用意する

git worktree は、1 つのリポジトリから複数の作業ディレクトリを切り出す機能です。これにより、Claude Code は todo-multi-ai/ で、Antigravity は別フォルダで、それぞれ別ブランチを同時に触れます。AI 同士の編集衝突を物理的に防げるのが利点です。

# main から refactor/todo ブランチを、隣のフォルダとして切り出す
$ git worktree add ../todo-refactor -b refactor/todo

# 現在の worktree 一覧を確認
$ git worktree list
# /path/todo-multi-ai     abc1234 [fix/bug-todo]
# /path/todo-refactor     def5678 [refactor/todo]
💡 用語補足 — worktree（ワークツリー）: 通常 1 リポジトリ＝1 作業フォルダですが、git worktree を使うと同じ .git を共有したまま複数のフォルダを作れます。各フォルダで別ブランチをチェックアウトできるので、「ブランチを切り替えるたびに作業が中断する」問題が起きません。並列 AI 開発と非常に相性が良い機能です。
📷 スクリーンショット差し込み位置
（git worktree list の出力 ＝ 2 つの作業フォルダが別ブランチを指している様子）

Step 2: Claude Code で高速デバッグ

本体フォルダ（fix/bug-todo ブランチ）で、仕込まれたバグを Claude Code に調査・修正させます。Claude Code はコードベース全体を読んだうえで対話的に原因を絞り込むのが得意なので、デバッグにうってつけです。

2-1. Claude Code を起動する

本体フォルダ（fix/bug-todo ブランチにいることを確認）で、Claude Code を起動します。

# 今いるブランチを確認（fix/bug-todo であること）
$ git branch --show-current

# Claude Code を起動
$ claude
📷 スクリーンショット差し込み位置
（fix/bug-todo ブランチで claude を起動した直後のターミナル）

2-2. バグを再現させ、原因を調べさせる

いきなり「直して」ではなく、「再現 → 原因特定 → 修正方針の提示」の順で対話するのが高速デバッグのコツです。次のプロンプトを使ってください。

▶ Claude Code へのプロンプト（原因調査）

この ToDo アプリで「完了済みタスクが一覧から消えない」というバグが報告されています。 まず、関連しそうなコードを読んで挙動を説明してください。 次に、バグの根本原因を 1 つに特定し、なぜそれが原因なのかを根拠（該当行）とともに示してください。 この時点ではまだコードは修正せず、原因の特定だけ行ってください。

🤔 「なぜ修正を急がせないのか」（プロの作法）
① 再現と原因の言語化を先にやらせる → ② 人間が原因の妥当性を確認する → ③ 納得してから修正させる。この順を守ると、「直ったように見えて別の場所を壊す」事故を防げます。AI に主導権を渡しつつ、判断のチェックポイントは人間が握るのが上級者の使い方です。

2-3. 修正させて、差分を確認する

原因に納得できたら、最小限の修正を依頼します。修正後は必ず git diff で自分の目で差分を確認します。

▶ Claude Code へのプロンプト（修正依頼）

特定してくれた原因に対して、最小限の修正を加えてください。 既存の挙動を壊さないよう、変更は該当箇所のみに留めてください。 修正後、何をどう変えたかを 3 行以内で要約してください。

# Claude Code が編集したファイルの差分を自分の目で確認
$ git diff

# 動作確認（題材アプリの実行）
$ node app.js   # もしくは npm test など
git diff は、ワークツリー（編集中の状態）とステージングエリアの差分を表示するコマンドです。AI が編集した内容は、コミット前に必ずこれで確認しましょう。
＜参考: 同書 4 章「変更内容を確認する／git diff」＞

2-4. add → commit でバグ修正を記録する

動作確認できたら、修正をステージング（git add）してコミット（git commit）します。コミットメッセージは Claude Code に作らせると速くて綺麗です。

# 変更をステージングエリアに追加
$ git add .

# 状態を確認（何がステージされたか）
$ git status

# コミット（メッセージは簡潔・明確に）
$ git commit -m "fix: 完了済みタスクのフィルタ条件を修正"

# リモートに push
$ git push origin fix/bug-todo
git add で変更をステージングエリアに移し、git commit -m でリポジトリに記録、git push でリモート（GitHub）に反映します。コミットメッセージは履歴を追う目印なので、簡潔かつ明確に書きましょう。
＜参考: 同書 4 章「git add / git status / git commit / git push」＞
💡 コミットメッセージも AI に任せる: Claude Code に「git diff --cached の内容から、Conventional Commits 形式のコミットメッセージを 1 行で提案して」と頼むと、差分から適切なメッセージを作ってくれます。CLI 型エージェントが Git と地続きであることの恩恵です。

⏱ 約 25 分 Antigravity

Step 3: Antigravity で並列リファクタリング

今度は、Step 1 で切り出した 別フォルダ（worktree）の refactor/todo ブランチで作業します。ここでは Antigravity の並列マルチエージェント機能を使い、コードの構造改善（リファクタリング）を行います。Claude Code が触っているフォルダとは別なので、編集が衝突しません。

3-1. worktree フォルダを Antigravity で開く

Step 1 で作った ../todo-refactor フォルダを Antigravity で開きます。本体フォルダ（Claude Code 側）はそのまま並行して動かしておいて構いません。

# worktree のフォルダへ移動して中身を確認
$ cd ../todo-refactor
$ git branch --show-current   # refactor/todo であること

# このフォルダを Antigravity で開く（コマンド名は環境に合わせて）
# 例: antigravity .   もしくは GUI からフォルダを開く
📷 スクリーンショット差し込み位置
（Antigravity で todo-refactor フォルダを開き、refactor/todo ブランチが表示されている様子）
💡 用語補足 — リファクタリング: 外から見た動作（挙動）を変えずに、内部の構造だけを綺麗にする作業のこと。「重複したコードを関数にまとめる」「長すぎる関数を分割する」「変数名を分かりやすくする」などが典型例です。動作が変わっていないことをテストで担保するのが鉄則です。

3-2. 並列マルチエージェントでリファクタを依頼する

Antigravity の強みは、独立した複数のタスクを並列に走らせられること。リファクタを「重複処理の関数化」「命名の改善」「コメント・型注釈の追加」のように分割し、それぞれをエージェントに割り当てます。

▶ Antigravity への指示（並列タスクの計画）

この ToDo アプリを、動作を変えずにリファクタリングしたいです。 次の 3 つを独立したタスクとして並列に進めてください。 1. 重複しているタスク操作ロジックを共通関数に切り出す 2. 変数・関数の命名を意図が伝わるものに改善する（camelCase 統一） 3. 主要関数に日本語のコメントを追加する 各タスクの変更は互いに矛盾しないよう調整し、最後に全体の差分概要を示してください。

⚠️ 並列実行で気をつけること: 複数エージェントを同時に走らせると、同じファイルの同じ箇所を別々に書き換えて矛盾することがあります。タスクは「触る範囲が重ならない単位」に分割し、Antigravity が提示する計画（Plan）と成果物（Artifacts）を人間が確認してから適用しましょう。

3-3. 動作確認してコミットする

リファクタは「動作が変わっていないこと」が命です。テストや実行で挙動を確認してから、refactor/todo ブランチにコミットします。

# worktree フォルダ内で動作確認
$ node app.js   # もしくは npm test

# 差分を確認してコミット
$ git add .
$ git commit -m "refactor: 重複ロジックの共通化と命名・コメントの改善"
$ git push origin refactor/todo
💡 ここまでの状態: fix/bug-todo（Claude Code のバグ修正）と refactor/todo（Antigravity のリファクタ）という、2 本の独立したブランチが GitHub 上に push されました。次の Step 4 で、これらを Git の作法に従って安全に統合します。

Step 4: Git で統合し PR を作成

ここが本コースの集大成です。2 つの AI が別ブランチで作った成果を、Git ワークフローに従って安全に統合し、GitHub に PR（プルリクエスト）を出すまでを通します。著者本人の Git 教材（『開発系エンジニアのための Git/GitHub 絵とき入門』5〜7 章）のエッセンスを、マルチAI開発の文脈に合わせて使います。

4-1. main を最新化する（git pull）

統合作業の前に、ローカルの main をリモートの最新状態に揃えます。チーム開発では、誰かの変更が先に入っていることがあるためです。

# 本体フォルダで main に切り替えて最新化
cd ../todo-multi-ai
git switch main
git pull --ff-only origin main

履歴が分かれていて停止した場合は、講師と確認してください。

git pull はリモートの変更を取得し、設定やオプションに従って取り込みます。統合前に main を最新にしておくと、後のコンフリクトを減らせます。
＜参考: 同書 6 章「変更内容を取得してすぐに反映する／git pull」＞

4-2. バグ修正ブランチを main にマージする（git merge）

まず Claude Code のバグ修正（fix/bug-todo）を main に統合します。

# マージ先（main）にいることを確認してからマージ
git switch main
git merge fix/bug-todo
git push origin main
git merge <ブランチ名> は、指定したブランチの変更を現在のブランチに統合します。マージは必ず「マージ先（取り込む側）」に切り替えてから実行します。
＜参考: 同書 5 章「ブランチをマージする／git merge」＞

4-3. リファクタ用に PR を作成する（プルリクエスト）

もう一方の refactor/todo は、いきなり merge せずプルリクエストを通してレビューしてもらう流れにします。これが「変更を他の人に確認してもらう」正攻法です。

# GitHub CLI で PR を作成（refactor/todo → main）
gh pr create --base main --head refactor/todo \
    --title "refactor: ToDo アプリの構造改善" \
    --body "Antigravity の並列エージェントで重複ロジックの共通化と命名改善を実施。動作は不変。"

# ブラウザで PR を確認
gh pr view refactor/todo --web
プルリクエスト（PR）は、自分の変更を他の人に見てもらい、レビュー・承認を求める仕組みです。GitHub 上で「New pull request」→ ベースブランチ（main）と変更ブランチ（refactor/todo）を選び、タイトルと説明を書いて作成します。
＜参考: 同書 6 章「プルリクエストを送信するまでの手順」＞
📷 スクリーンショット差し込み位置
（GitHub の PR 作成画面 — base: main / compare: refactor/todo）
💡 マルチAIならではの PR の使い方: PR の説明欄に「どの AI が・どのブランチで・何をやったか」を明記しておくと、レビュー時に「この変更は Antigravity の並列リファクタ由来」と一目で分かり、レビューの精度が上がります。さらに別の AI（Codex など）に PR の差分レビューを依頼するのも有効です。

4-4. コンフリクトが起きたら解決する（conflict）

バグ修正とリファクタが同じファイルの同じ行を触っていた場合、PR のマージ時にコンフリクト（衝突）が起きます。マルチAI開発では「別 AI が同じ箇所を直す」ことがあるため、避けて通れません。落ち着いて解決しましょう。

# PR をマージしようとしてコンフリクトが出たら、ローカルで解決する
cd ../todo-refactor
git branch --show-current   # refactor/todo と表示されることを確認
git merge main          # ここでコンフリクト発生

# どのファイルが衝突したか確認
git status

衝突したファイルを開くと、次のようなコンフリクトマーカーが入っています。どちらを残すか（または両方を活かすか）を判断し、マーカーごと正しい形に書き直します。

<<<<<<< HEAD
（refactor/todo 側 ＝ Antigravity の変更）
=======
（main 側 ＝ Claude Code のバグ修正）
>>>>>>> main
# 解決したらマーカーを消して保存し、ステージング→コミット
$ git add app.js
$ git commit -m "fix: バグ修正とリファクタのコンフリクトを解決"
$ git push origin refactor/todo   # PR が自動更新される
コンフリクトは、同じファイルの同じ箇所を別々に変更したときに発生します。<<<<<<< / ======= / >>>>>>> のマーカーを目印に正しい内容へ直し、マーカーを削除して git add → git commit で解決を記録します。片方だけ採用するなら git checkout --ours / --theirs も使えます。
＜参考: 同書 7 章「複数の人が行った変更の交通整理をしよう（コンフリクト）」＞

4-5. マージしてブランチを片付ける

レビューが通ったら PR をマージし、不要になったブランチと worktree を掃除します。

# 本体フォルダへ戻り、main に切り替えて PR をマージ
cd ../todo-multi-ai
git switch main
gh pr merge refactor/todo --merge
git pull --ff-only origin main

# ローカルの後片付け：worktree を外し、ブランチを削除
git worktree remove ../todo-refactor
git branch -d fix/bug-todo refactor/todo
マージ済みのローカルブランチは git branch -d <名前> で削除できます（未マージを強制削除する -D は慎重に）。リモートブランチは git push origin --delete <名前> または GitHub の「Delete branch」で削除します。
＜参考: 同書 5 章「ブランチを削除する」・6 章「リモートブランチの削除」＞

Step 5: 複数AI併用のベストプラクティス

最後に、複数の AI エージェントを同時に使うときに環境を干渉させないためのコツを整理します。ここを押さえると、マルチAI開発が「速いけど壊れる」から「速くて安全」に変わります。

5-1. 干渉を防ぐ 4 つの原則

原則 具体策 なぜ効くか
① 作業領域を分ける AI ごとにブランチ＋ git worktree で別フォルダにする 同じファイルを同時に書き換える事故を物理的に防ぐ
② 役割を分ける 「調査・デバッグ＝Claude Code」「並列実装＝Antigravity / Codex」と固定 得意分野に集中させ、品質とスピードを両立
③ 統合は人間＋Git マージ・PR・コンフリクト解決は人間が Git で行う 最終判断の責任を人間が握り、履歴を綺麗に保つ
④ 設定を共有しすぎない グローバル設定・依存・ポートが衝突しないか確認 複数 AI 起動時のリソース・ポート競合を避ける

5-2. 環境干渉のよくある落とし穴と対策

  • 同じポートで開発サーバーを起動して衝突 → worktree ごとにポートを分ける（例: 本体 3000 / リファクタ 3001）。
  • node_modules の共有による不整合 → worktree は依存を共有しないため、各フォルダで npm install を実行する。
  • 2 つの AI が同時に同じブランチへ commit → ブランチは「1 AI 1 ブランチ」を厳守。原則 ② と ① の合わせ技で防ぐ。
  • AI が勝手に git push --force 等の破壊的操作 → 破壊的コマンドは人間が手動で。AI には「push や force は行わず提案だけして」と伝える。
⚠️ いちばん危険なのは git reset --hard と force push。これらは変更を復元できない形で消す可能性があります。AI に任せず、必要なときだけ人間が内容を理解した上で実行してください。
＜参考: 同書 4 章「git reset / git checkout」の注意書き＞

5-3. チームに展開するときの指針

  • 命名規則を決める: fix/・refactor/・feat/ の接頭辞で、どの種類の作業かを一目で分かるようにする。
  • PR テンプレに「使った AI」を書く欄を作る: レビュー時の文脈になる。
  • CI でテストを必須化: AI のリファクタが「動作を変えていない」ことを機械的に担保する。
